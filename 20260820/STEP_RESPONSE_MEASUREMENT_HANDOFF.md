# 階段状トラップジャンプ計測 — 実機側への引き継ぎ

**作成: 2026-08-21 / 引き継ぎ先: 実機PC (OpenMPD + ステレオイベントカメラ) 側の作業者・エージェント**

このドキュメントだけで実機収録まで到達できるように書いています。解析側 (Miyabi/ローカル) の
作業は済んでおり、**残るのはハードウェア再生部の接続と実収録だけ**です。

---

## 1. 何をする計測か（1段落で）

音響トラップの指令位置 `u` を **階段状に瞬間ジャンプ** させ、粒子が新しいトラップ位置へ
自由減衰していく様子を記録します。学習対象は `e = x − u`（粒子とトラップの相対オフセット）で、
ジャンプ直後に `e` はステップ幅まで跳ね上がり、そこから減衰します。
**ホールド中は `u̇ = ü = 0` が厳密に成立する**ため、制御項を一切含まない
`ë = f(e, ė)` を単独同定できます。これが目的です。

> **重要**: 粒子をピンセット等で動かすのではありません。**粒子は触らず、トラップ側だけを飛ばします。**
> `e` のダイナミクスとしては数学的に等価で、かつ実機で唯一現実的な方法です。

---

## 2. なぜ必要か（背景・省略可だが読むと判断が速い）

既存の連続軌道データ (`stereo_acoustools_3d_records_auto*`, 40 runs) を使った
SINDYc グリッドサーチで、以下が判明しています:

- 候補ライブラリの **condition_number が全診断 3900 件中 100% で Infinity**、
  列間相互コヒーレンスが平均 **0.994〜0.995**（＝設計行列が常に数値的に特異）
- 追従が良い軌道では `e` が狭帯域に閉じ込められ、`sin(2k·e)` 高調波と低次 `e` 冪、
  さらに制御項 `u, u̇, ü` までが互いにほぼ線形従属になる（典型的な閉ループ同定問題）
- ridge_alpha を 1e-6→1e-3 に上げる等の回帰側の対症療法では
  rollout 比 3.38→2.84 までしか改善せず、**baseline(=1.0) に届かない**

つまり回帰手法をいくら工夫しても限界で、**「u が動かないデータ」を新規に取る**のが本筋です。
既存 79 試行のホールド区間は**合計わずか 1 秒**しかありませんでした。
本計測のティア A（3収録・20.4秒）だけで約 **20 秒**、全ティアで約 **145 秒** が得られます。

## 3. 実装済みのもの（このリポジトリに入っています）

| ファイル | 役割 | 状態 |
|---|---|---|
| `Acoutools_eventcam/hf_identification_trajectory.py` | 軌道生成器。`kind: "staircase"` を新規追加済み | ✅ 実装・検証済 |
| `Acoutools_eventcam/step_response_identification_plan.json` | 計測プラン（ティアA/B/C） | ✅ 作成済 |
| `sindy_stereo3d_free_response.py` | 解析側 2 段階 SINDy（Stage A/B）。`detect_hold_segments()` 含む | ✅ 実装済（本計測より前から存在） |

### 生成器の使い方

```bash
cd Acoutools_eventcam
python3 hf_identification_trajectory.py \
    --plan step_response_identification_plan.json \
    --output-dir step_response_export
# ティアB/Cも一緒に書き出したい場合は --include-disabled を付ける
```

各実験ごとに `step_response_export/<name>/` が作られ、中身は:

```
command_trajectory.npz      # keys: time_sec, offset_mm(N,3), offset_m(N,3), sample_hz
trajectory_metadata.json    # 生成条件・安全マージン・ジャンプ時刻リスト
trajectory_preview.png      # 目視確認用（脱出境界・力最大点の線入り）
```

**`offset_mm` は浮揚中心からのオフセット** です。実機コードは自分の中心座標を足してください
（`positions_about_center(offset_mm, center_m)` が同ファイルに用意されています）。

### staircase 種別で既存コードと違う点（実装済み、注意点として把握だけ）

通常の chirp/multisine 用パスをそのまま通すと壊れるため、2 箇所を意図的にバイパスしています:

1. **`smooth_envelope` を通さない** — sin² ランプが「実験の本体であるステップの角」を丸めるため
2. **`_safety_scale` を通さず振幅ベース検査 `_staircase_safety_check` に置換** —
   ステップは意図的な不連続なので微分した加速度が発散し、既存の
   `max_acceleration_mm_s2 = 28000` 制限だと軌道が **約 1/3600 に潰されて無意味**になる。
   代わりに「指令オフセットと 1 ジャンプ幅が脱出境界を超えないこと」を検査する。

## 4. 物理から決めた安全境界（**必読**）

40 kHz、λ = 8.575 mm、k = 2π/λ = 0.7327 rad/mm。
Gor'kov 復元力 ∝ `sin(2k·e)` なので:

| | オフセット | 意味 |
|---|---|---|
| 力の最大 | **1.072 mm** | 非線形性が最も強い＝同定に最も美味しい点 |
| 力ゼロ＝**脱出境界** | **2.144 mm** | **超えると力が反転し隣のノードへ飛んで粒子ロスト** |

`_staircase_safety_check` はジャンプ幅が脱出境界以上なら例外を投げます。

### 安全側の根拠

既存の粒子搬送コード (`acoustools_eventcam_sync_auto.py`) が
`AUTO_TRANSFER_STEP_MM = 0.25` / `AUTO_TRANSFER_DWELL_SEC = 0.04` を常用しており、
**0.25 mm ステップは実績あり**と判断しました。そこから段階的に上げます。

## 5. 計測プラン（3 ティア・段階的エスカレーション）

| ティア | 軸 | 振幅 [mm] | 最大ステップ | 脱出境界比 | 1収録 | 収録数 | 計 | 既定 |
|---|---|---|---|---|---|---|---|---|
| **A** | x/y/z | 0.25, 0.4 | 0.40 mm | 19% | 6.8 s | 3 | 20.4 s | `enabled: true` |
| **B** | x/y/z | 0.25, 0.5, 0.7 | 0.70 mm | 33% | 9.2 s | 6 | 55.2 s | `enabled: false` |
| **C** | x/y/z | 0.3, 0.6, 0.85, 1.05 | 1.05 mm | 49% | 11.6 s | 6 | 69.6 s | `enabled: false` |

**エスカレーション手順（守ってください）**:
1. まず **ティア A のみ**を流し、**全ジャンプで粒子が生存する**ことを確認
2. 生存を確認したら plan JSON の B を `"enabled": true` にして実行
3. 同様に確認できたら C を有効化

ティア C は力の最大点 (1.072 mm) に狙って乗せてあり、非線形性の同定に最も効きますが、
リスクも最大です。**粒子をロストしたら再浮揚が必要**なので、必ず A→B→C の順で。

### 各収録の構造

```
u(t): 0 →(2.0s 保持)→ +a₁ →(0.3s)→ 0 →(0.3s)→ −a₂ →(0.3s)→ 0 → ...
```

- **先頭 2.0 秒は中心で静止**（粒子を完全に落ち着かせ、重力サグ等の DC オフセットを測る。
  解析側 `--dc-calib-sec 2.0` と対応）
- 各プローブは**必ず中心へ戻る**。往路・復路の**両方が有効なステップ応答**なので無駄がなく、
  かつ指令位置が校正済み領域内に留まる
- 振幅・符号の順序は `order_seed` でランダム化済み（系統的ドリフトとの交絡を防ぐ）
- ホールド 300 ms は、γ=30 1/s（最悪ケース）でも 9τ、88 Hz 共振の 26 周期に相当

## 6. ★残作業★ ハードウェア再生部の接続

**ここが唯一の未着手部分です。**

現状 `hf_identification_trajectory.py` は**スタンドアロン**で、実際の収録を駆動している
`acoustools_eventcam_sync_auto.py`（独自の `SHAPE_TO_MODE` レジストリ、mode 1〜11）とは
**繋がっていません**。実機で流すには次のどちらかが必要です:

### 案 (b) — 推奨: エクスポート済み npz を再生する小ドライバ

既存のハードウェアコードを一切書き換えずに済むため安全です。やること:

1. `command_trajectory.npz` の `offset_mm` を読む
2. 中心座標を足して絶対位置列にする（`positions_about_center()` が使える）
3. 既存の収録フロー（PAT 再生 + ステレオイベントカメラ同期 + `ideal_log` 出力）に流す

### 案 (a) — `acoustools_eventcam_sync.py` に新 mode を追加

既存の自動収録ループにそのまま乗るが、ハードウェアコード本体を触ることになる。

> **判断待ち**: どちらで行くかは未決です。特段の理由がなければ **(b)** を推奨します。

### 再生時の必須要件

| 項目 | 値 | 根拠 |
|---|---|---|
| PAT 更新レート | **10000 Hz** | 既存収録の `pat_fps_actual` と一致。40000 の正確な約数（divider=4） |
| PAT ベースクロック | 40000 Hz | `PAT_UPDATE_BASE_HZ` |
| 最低フレームレート | 157 Hz | `PAT_MIN_FRAME_RATE_HZ`（10000 Hz なら問題なし） |
| イベントカメラ | 10000 fps (dt=100 µs) | 既存ステレオ収録と同じ |

**タイミング精度について**: `move_static_position()` 系の `time.sleep()` ベースの
Python ループ（搬送用）は ms オーダのジッタがあるため、**本計測の再生には使わないでください**。
軌道再生はハードウェアタイミングの経路（`PAT_UPDATE_BASE_HZ / divider`）に乗せる必要があります。
ホールドが 300 ms あるので多少のジッタは許容されますが、ジャンプ時刻が
`trajectory_metadata.json` の `jump_times_sec` と大きくずれないことが望ましいです。

## 8. 収録後の検証方法

解析側で最初にこれを回してください。ホールド区間が期待通り検出されるかの確認です:

```bash
python3 sindy_stereo3d_free_response.py detect \
    --base-dir Acoutools_eventcam \
    --vel-tol-mm-s 1.0 \
    --min-hold-sec 0.05
```

**期待値**（合成データによる end-to-end 検証で確認済み）:

- ティア A の 1 収録あたり **17 hold segments**（先頭 2000 ms + 300 ms × 16）
- 収録時間の **99.8%** がホールド区間として使える
- 指令が変化するサンプルは 68000 点中 **16 点のみ (0.024%)**
  → **99.976% のサンプルで u̇ = ü = 0 が厳密成立**

この数字から大きく外れる場合は、再生のスムージング（ランプが掛かっている等）を疑ってください。

## 9. 解析側の申し送り（実機側は対応不要）

- Stage A は減衰トランジェント（τ = 12〜33 ms、88 Hz）を見るため、
  現行の `--weak-half-width-ms 30`（窓幅 60 ms ≈ 共振 5 周期分）は平均化が効きすぎる可能性がある。
  **Stage A のみ 5〜10 ms に下げて比較する**価値がある。合成データでは 5/15/30 ms
  いずれでも 17 segments すべてが usable だったので、下げても区間数は減らない。
- 参考: 決定論モデルの改善率には**理論上限 26.6%** がある
  （既存データのコヒーレンス解析より。88 Hz 共振は u と無相関＝音響ストリーミング等の確率的擾乱）。
  目標は「誤差ゼロ」ではなく **NoModel 比 +26.6% に近づくこと**。
